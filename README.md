# AI Content Production System

An AI-powered content production platform for generating, revising, and validating web content through a structured production pipeline.

## Overview

The AI Content Production System combines research, strategy, content generation, revision, and quality assurance into a single Streamlit-based workflow.

The system is designed to produce controlled, brand-aware content while applying deterministic rules and AI-assisted QA before content is considered ready for delivery.

## Key Capabilities

- Strategy and content planning
- Research and evidence collection
- AI-assisted content generation
- Content revision
- Deterministic rule validation
- AI-assisted QA and validation
- Reference website/style analysis
- Brand and canonical content rules
- Gemini + Groq provider routing and fallback
- Purpose-specific API key configuration
- Provider cooldown and quota-aware handling
- Pipeline caching
- Streamlit Studio and Configuration interfaces

## AI Provider Configuration

The application supports Gemini and Groq providers with purpose-specific configuration for areas such as:

- Research
- Strategy
- Generation
- QA

Example environment variables are provided in `.env.example`.

**Never commit real API keys, passwords, or other secrets to GitHub.**

### Request routing and token budget (Phase 1)

With both providers configured, every request is planned before it is sent: estimated input + the output cap that is enforced +
any search overhead, compared with every limit that applies (context, tokens/minute including what was used in the last minute,
tokens/day, requests/minute, requests/day). The target is **25% headroom**, the floor **20%**, and no request ever uses more than
**80%** of a limit. If nothing fits, the step pauses before any risky call and resumes later from the saved steps.

* **Your keys and purposes are unchanged.** Each purpose keeps its own key(s) with the shared key as backup, in that order; a key that
  hits its limit rests and the next key is used. The router plans on each key, not on "Gemini" as a whole.
* **Quota is per Google project (Gemini) and per organisation (Groq), and per model.** Nothing is assumed about which keys share a
  project: keys you have not declared are *unverified* and treated as ONE shared quota. Declare groups in the Configuration tab
  (or `GEMINI_KEY_GROUPS` / `GROQ_KEY_GROUPS`), or let the system learn them (a provider error that names the project or organisation, or
  a key that works right after another was limited). See *Configuration → Maintenance → Quota groups*.
* **Verified Gemini limits** (free tier, `gemini-3.6-flash`): 5 requests/minute, 250,000 tokens/minute, 20 requests/day. They are
  configurable per project and model; other models and projects are assumed to be no better until you enter theirs. With 20
  requests/day a project supports roughly 3 typical workflows a day at 25% headroom.
* **Gemini output cap:** a Gemini request carries exactly the output cap the planner reserved. Gemini counts hidden thinking tokens
  inside that cap, so the reservation has a minimum (default 8192, configurable).
* **Gemini** reads, writes and audits (large context). **Groq** does web research with its built-in `browser_search`.
* **Gemini Google Search grounding is never assumed.** It is tried at most once per key and model, then remembered; a failure is never
  repeated. If you confirm it for your project, set *Gemini Google Search grounding* to `yes`.
* **Rules per stage:** each stage receives only the sections listed in `data/rules/profiles.json` (draft: needs the rule owner's
  sign-off). A section that cannot be found makes the whole document go out in full. Set *Rule documents per stage* to `off` to send
  everything everywhere.
* **Evidence is never trimmed to fit.** QA receives the complete draft and every claim. A Revamp source page too big for the research
  route is reduced to a *verified verbatim digest* (the page's own sentences, kept when anything in them looks like a fact: numbers,
  dates, prices, URLs, names, rules, obligations, contact details; anything the model "extracted" that is not in the page is dropped).
  If the digest cannot be trusted, the full page is used or the run pauses. The blueprint always sees the full page.
* **Per-stage model variables** (`GEMINI_MODEL_QA` and friends) are preserved and shown but not applied unless you switch them on.
* **Usage log:** real token counts per call (provider, model, stage, quota group, cached tokens, duration; never prompts or keys).
* Run the tests with `python -m pytest tests -q` (no network or API keys needed).

## Local Setup

### 1. Clone the repository

```bash
git clone https://github.com/Yash092005/AI_Content_Production_System.git
cd AI_Content_Production_System
```

### 2. Create a virtual environment

Windows:

```bash
python -m venv .venv
.venv\Scripts\activate
```

macOS/Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
```

### 4. Configure environment variables

Copy `.env.example` to `.env` and configure the required provider credentials and application settings.

Do not commit `.env`.

### 5. Run the application

```bash
streamlit run app.py
```

## Configuration & Rules

The application loads its content-governance and production rules from the `data/rules/` directory.

These files include:

- Master Instructions
- Canonical Specification
- Brand Constitution
- Rule documentation

The Configuration page in the application provides access to the relevant production configuration and rule status.

## Security

The repository intentionally excludes sensitive and development-only files, including:

```text
.env
.streamlit/secrets.toml
.cache/
.pytest_cache/
__pycache__/
*.pyc
tests/
```

Only example configuration files should be committed when they do not contain real credentials.
